# ETL

원본 데이터 적재·검수·그래프 빌드. 계획서 §5·§6 참조.

## 환경

**시스템 파이썬에 설치하지 않는다.** venv를 쓴다.

```bash
py -m venv .venv
./.venv/Scripts/python.exe -m pip install -r etl/requirements.txt
```

Linux/macOS는 `.venv/bin/python`.

## 원본 데이터

`csv/`는 저장소에 없다 (340MB, 최대 파일 154MB — GitHub 단일 파일 한도 초과).
출처와 수신 방법은 계획서 §3의 데이터 표를 따른다. 배치는 이렇게 둔다.

```
csv/
  장소/    식품_일반음식점_서울특별시.csv, 식품_휴게음식점_서울특별시.csv
  지하철/  도시철도열차운행시각표(역간 소요시간 + 시간대별 배차, 1~9호선),
           환승역거리 소요시간, 역사마스터, 역간거리 및 소요시간, 열차운행현황(대조용)
  버스/    노선마스터, 정류장마스터, 구간별 평균 운행시간(tpss_route_section_speedh_*),
           노선기본정보(배차간격, xlsx), 노선ID정보(조인키, xlsx)
```

키가 서로 다른 데이터를 잇는 경로가 둘 있다.

- 버스: `노선번호` ──[노선ID정보]──▶ `ROUTEID` ──▶ 구간 데이터 `노선_ID` (서울 693노선 100%)
- 지하철: 시각표 `(LINE, STATION_NM)` ──[노선명 매핑]──▶ 역사마스터 `(호선, 역사명)` (98.0%)
  역사마스터가 1호선 바깥을 경부선·경인선·경원선, 4호선을 안산선·과천선 등으로 담고 있어 매핑이 필요하다.

**인코딩이 파일마다 다르다.** 대부분 CP949(EUC-KR)인데 **열차운행시각표만 UTF-8 BOM**이다.
자동 감지에 기대지 말고 파일별로 지정할 것.

원본 좌표계가 둘로 갈린다 — POI는 **EPSG:5174**(`좌표정보(X)/(Y)`), 정류장·역사는
**EPSG:4326**(위도/경도). 저장은 전부 **EPSG:5186**으로 통일한다.

## fetch — 인허가 원본 받기

```bash
./.venv/Scripts/python.exe -X utf8 -m etl.fetch --source all     # food | rest | all
```

`csv/장소/` 의 두 파일을 최신으로 바꾼다. 일일 실행(`run_daily.cmd`)이 적재 앞에서 부른다.
**API 키가 필요 없다.**

| | |
|---|---|
| 출처 | `file.localdata.go.kr` — 공공데이터포털 데이터셋(「행정안전부_일반음식점」 15045016 등)이 안내하는 제공 방식. LOCALDATA 는 2026-04 공공데이터포털로 이전됐고 이 데이터의 오픈API 는 없다 |
| 이용허락 | 제한 없음. 매일 2일 전 기준으로 갱신 |
| 서울 전체 | `/file/download/general_restaurants/info?orgCode=6110000_ALL` (161.9MB), `rest_cafes` (46.9MB). `6110000` 만 쓰면 본청 소관만 온다 |
| 서버 규칙 | `Referer` 가 없으면 오류 페이지로 보낸다 → 사이트 버튼처럼 그 업종의 안내 페이지를 붙인다. 받기 전 `/file/validate/download-count` 로 횟수를 묻고 429 면 멈춘다 |
| 안전장치 | `.part` 로 받아 **서버가 준 파일 이름 · 39컬럼 헤더(CP949) · 크기(기존의 80% 이상)** 를 확인한 것만 제자리로 옮긴다. 실패하면 기존 파일을 건드리지 않고 종료 코드 4 |

받기만 한다. 바뀌었는지는 `ingest` 가 해시로 판정한다.

**실측 (2026-09-22)**: 일반 161,825,149B → 161,930,815B (46.2초), 휴게 46,902,891B → 46,943,182B (13.2초).
이어진 적재에서 신규 446 · 폐업 전환 527 · 소멸 0 · 좌표 이동 13.

## ingest — 인허가 적재 (단일 진입점)

```bash
docker compose up -d db
docker compose --profile migrate run --rm flyway

./.venv/Scripts/python.exe -X utf8 -m etl.ingest --source all
```

```
CSV (CP949)  ──COPY──▶  poi_raw  ──변환·중복제거──▶  poi_staging
                                                        │ 검수 규칙
                                                        ▼
                                              validation_result
                                                        │ ERROR 제외분
                                                        ▼
                                                      poi
```

| 옵션 | |
|---|---|
| `--source food\|rest\|all` | 적재 대상 |
| `--limit N` | 앞 N행만 (시험용) |
| `--force` | 파일 해시가 같아도 다시 적재 |
| `--snapshot PATH` | 원본 경로 덮어쓰기. 다른 회차 스냅샷이나 실패 격리 시험용 |

**실측 (2026-09-15)**: 서울 전체 685,718행(일반 538,576 + 휴게 147,142) **2분 28초**.
**실측 (2026-09-22, 첫 일일 회차)**: 686,164행 **3분 10초**.
serving `poi` 646,418건 — ACTIVE 154,669 / CLOSED 491,749.

### 알아둘 것

- **좌표 변환은 여기서만** 한다. DB는 `ST_Transform` 을 쓰지 않는다 (`verify_db_crs.py` 참조)
- staging 적재 직후 **`ANALYZE poi_staging` 이 필수**다. 트랜잭션 안이라 autoanalyze 가 손대지 못하는데,
  통계가 낡으면 `DUPLICATE_NAME_ADDR` 조인이 nested loop 로 풀려 **8분 넘게** 걸린다 (실측)
- `poi_staging` 은 현재·직전 회차만 남기고 정리한다. 안 그러면 회차마다 수십만 행씩 쌓여
  일일 자동 실행 열흘이면 500만 행이 된다
- 실패하면 회차가 FAILED 로 남고 **serving 은 무변경**이다 (단일 트랜잭션)

## 일일 자동 실행

```cmd
etl\register_daily_task.cmd
```

Windows 작업 스케줄러에 `WhereWeGo-DailyIngest` 를 **매일 22:00** 으로 등록한다.
순서는 **받기(`etl.fetch`) → 적재(`etl.ingest`)**. 받기가 실패하면 기존 파일로 적재하고 종료 코드 4 를 남긴다.
처음엔 받기 단계가 없어 매일 같은 파일을 해시만 보고 SKIPPED 로 끝났다(2026-09-22 22:00 회차).
관리자 권한이 필요 없다. LOCALDATA 가 2일 전 기준으로 갱신되므로 늦게 돌려도 잃는 것이 없다.

처음에는 04:30 이었는데 **한 번도 돌지 않았다.** 두 가지가 겹쳤다.

1. 이 노트북은 모던 스탠바이(S0)라 예약 작업의 절전 해제 타이머를 무시한다. 04:30 에 깨지 않았다.
2. 놓친 실행은 켜질 때 돌도록 해 두었지만, 기본 조건인 "배터리일 때 시작 안 함" 이 남아 있었다.
   아침에 충전기 없이 노트북을 열자 그 조건에 걸려 거부됐다.

그래서 평소 켜 두는 시각으로 옮기고, 등록 스크립트가 다음 조건을 함께 건다
(`schtasks /Create` 는 조건을 기본값으로 되돌리므로 다시 등록해도 풀리지 않게).

| 조건 | 값 | 이유 |
|---|---|---|
| 놓친 예약은 켜질 때 바로 실행 | 켬 | 22:00 에 꺼져 있었어도 다음에 켤 때 돈다 |
| 배터리일 때 시작 안 함 | **끔** | 놓친 실행은 대개 충전기 없이 열 때 돈다 |
| 절전 중이면 깨워서 실행 | 켬 | 모던 스탠바이에서는 무시되지만 해가 없다 |

| | |
|---|---|
| 즉시 실행 | `schtasks /Run /TN "WhereWeGo-DailyIngest"` |
| 상태 확인 | `schtasks /Query /TN "WhereWeGo-DailyIngest" /V /FO LIST` |
| 해제 | `schtasks /Delete /TN "WhereWeGo-DailyIngest" /F` |
| 로그 | `etl/out/logs/ingest-YYYYMMDD.log` |

**목적은 회차를 쌓는 것이다.** `/admin/ingest-runs` 표가 README 의 증거인데 회차가 한둘이면
파이프라인이 돌고 있다는 것이 보이지 않는다. 일찍 걸수록 많이 쌓인다.

### 도커가 꺼져 있는 날

`ingest` 는 DB 에 닿지 못하면 **회차를 만들지 않고 종료 코드 3** 으로 물러난다.
`run_daily.cmd` 가 이를 0 으로 바꿔 스케줄러 기록에 실패로 남기지 않는다.

적재를 시도하다 깨진 것(FAILED)과 아예 시작하지 못한 것은 다른 사건이다. 구분하지 않으면
도커를 안 켠 날마다 FAILED 가 쌓여 `/admin/ingest-runs` 가 "자주 깨지는 파이프라인"처럼 읽힌다.

### 스크립트가 ASCII 전용인 이유

`run_daily.cmd` 와 `register_daily_task.cmd` 에는 한글 주석이 없다. 스케줄러가 어떤 콘솔
코드페이지로 부를지 알 수 없고, CP949 가 아닌 환경에서 한글 주석이 깨지면 **주석 조각이
명령으로 실행된다**(실제로 겪었다). 설명은 이 문서에 둔다.

배치의 함정 하나 더 — `echo ... %CODE%>> file` 은 값이 숫자로 끝나면 `0>>` 가 **스트림 0
리다이렉션**으로 해석돼 값이 사라진다. 리다이렉션을 앞으로 뺀다(`>> file echo ...`).

## subway_timing — 역간 소요시간 · 시간대별 배차

시각표 한 파일에서 그래프 빌드에 필요한 두 값을 뽑는다.

```bash
./.venv/Scripts/python.exe -X utf8 -m etl.subway_timing --out etl/out/subway
./.venv/Scripts/python.exe -X utf8 -m etl.subway_timing --weektag SAT --out etl/out/subway
```

| 산출 | 묶는 기준 |
|---|---|
| 역간 소요시간 | `(LINE, INOUTTAG, TRAIN_NO)` → 연속 역의 시각 차 |
| 시간대별 배차 | `(SI_ID, INOUTTAG)` → 연속 열차의 도착 시각 차 |

**핵심은 `TRAIN_NO`** 다. 열차를 특정할 수 없으면 "같은 열차가 다음 역에 도착한 시각"을
묶을 수 없어 역간 소요시간이 안 나온다.

**결과 (주중, 2026-09-15)**: 유효 159,221행 · 고유 구간 993개(9호선 102 포함) ·
주행 중앙 100초 · 역 좌표 매핑 453/458(98.9%).

주중 배차 중앙(분):

| 호선 | 8시 | 12시 | 19시 | 22시 |
|---|---|---|---|---|
| 2 | 3.2 | 6.0 | 3.5 | 6.0 |
| 7 | 4.0 | 6.0 | 5.0 | 8.2 |
| 9 | 6.3 | 11.0 | 6.8 | 11.0 |

### 종착지로 쪼개지 말 것

배차를 `(역, 방향, **종착지**)` 로 묶으면 **2~4배 부풀려진다.** 1호선 8시대가 종착지별로는
13.0분, `(역, 방향)` 만으로는 4.5분, 운행현황 참조값은 3분이다. 시청역 가는 승객은
인천행이든 신창행이든 아무 하행이나 타므로 `(역, 방향)` 이 맞다.

분기 목적지에 따라 실제 대기가 더 길 수 있다는 한계는 README 에 적는다 — 정확히 다루려면
경로 의존 모델이 필요하고 범위를 넘는다. 이 선택은 테스트로 고정해 뒀다
(`test_does_not_split_by_destination`).

### 참조값과 범위를 맞출 것

대조에 쓰는 서울교통공사 「열차운행현황」은 **공사가 직접 운영하는 구간만** 잰다
(1호선은 서울역~청량리). 시각표는 코레일 직결 전체(양주~인천)를 담는다. 범위를 맞추지 않으면
멀쩡한 산출값이 1호선 2.67배, 4호선 2.4배로 튄다 — 실측하면 이렇다.

| | 공사 구간 | 그 밖 |
|---|---|---|
| 1호선 | 3.5분 | 8.0분 |
| 4호선 | 3.0분 | 6.5분 |

외곽 지선은 실제로 배차가 길다. **방법이 틀린 것이 아니라 재는 대상이 다른 것이다.**
`REFERENCE_SCOPE_STATIONS` 가 이를 맞춘다.

### 그 밖의 함정

- `STT` 최대값이 `25:14:00` 이다(영업일 기준, 24시=익일 0시). `time` 으로 파싱하면 깨진다
- 시·종착역은 도착 또는 출발 시각이 비어 있다(약 15,000행). 서로 채운 뒤 남는 것만 버린다
- 급행은 기본적으로 제외한다. 섞으면 배차가 짧아 보이는데, 급행이 안 서는 목적지로 가는
  승객에겐 탈 수 없는 열차다
- 역사마스터가 1호선 바깥을 **경부선·경인선·경원선**, 4호선을 **안산선·과천선**으로 담는다.
  `LINE_ALIAS` 없이는 70.6%, 있으면 98.9% 가 붙는다

## verify_coords — 좌표계 판정 (D0)

인허가 좌표의 원본 좌표계를 앵커 대조로 판정한다. 어느 EPSG인지 파일에 적혀 있지 않고,
잘못 고르면 **전체가 같은 방향으로 수백 미터 밀려** 지도에서 눈으로는 잡히지 않는다.

```bash
./.venv/Scripts/python.exe -X utf8 -m etl.verify_coords --out etl/out/coord_verification.json
```

전체(50만 행) 기준 2분쯤 걸린다. 빠르게 보려면 `--nrows 200000`.

터미널이 한글을 못 찍으면 `-X utf8`과 함께 `chcp 65001`(Windows) 또는 출력을 파일로 받는다.

**결과 (2026-09-14)**: 원본은 5174 계열 확정(`lon_0 = 127.0028902777778`). datum shift 방식은
결과에 무관(이격 최대 21.3m). 상세는 계획서 §6 D0과 `out/coord_verification.json`.

### 앵커를 고칠 때

`ANCHORS`의 위경도는 **손으로 넣은 참조값**이다. 잔여 오차 ~124m의 대부분이 여기서 온다
(63빌딩 8.5m vs 고속터미널 206.2m). 오차가 크게 나오면 변환보다 이 표를 먼저 의심할 것.

## verify_crs_alignment — 좌표계 정합 교차 검증

POI(5174)와 버스 정류장(4326)을 5186으로 통일했을 때 실제로 겹치는지 확인한다.
앵커를 사람이 입력하지 않고 **정류장 11,494개를 기준으로** 쓰므로 `verify_coords`보다 독립적이다.

```bash
./.venv/Scripts/python.exe -X utf8 -m etl.verify_crs_alignment --out etl/out/crs_alignment.json
```

**결과 (2026-09-14)**: 채택 좌표계에서 POI→최근접 정류장 중앙 **80.5m**, 100m 이내 62.6%.
음성 대조군(5186으로 오인)은 88km. 정합 확인.

## verify_db_crs — ETL ↔ DB 좌표 변환 일치 확인

좌표 변환은 ETL(pyproj)에서만 하고 DB는 저장만 한다. 그래도 두 엔진이 같은 EPSG 코드를
다르게 해석하지 않는지는 확인해야 한다 — 어긋나면 반경 검색과 스냅 거리가 조용히 틀어진다.

```bash
docker compose up -d db
./.venv/Scripts/python.exe -X utf8 -m etl.verify_db_crs
```

**결과 (2026-09-15)**: 표본 1,000점 최대 차이 **0.000000m**.
pyproj(PROJ 9.4.1)과 PostGIS 3.5가 EPSG:5174→5186을 동일하게 해석한다.

DB 셋업 직후와 PROJ·PostGIS 버전을 올릴 때마다 돌린다. **허용치(1mm)를 늘려 통과시키지 말 것.**

## 테스트

```bash
./.venv/Scripts/python.exe -m pytest -q
```

원본 CSV에 의존하지 않는다 — CSV가 필요한 테스트는 CP949 픽스처를 그때그때 만든다.
