## 2. 다익스트라 1회

출발지는 무작위 보행 노드 300곳. 행렬 한 줄이 이 탐색 한 번이다.

| 탐색 | 중앙값 | p95 | 최대 | 확정 노드(중앙값) |
|---|---|---|---|---|
| 후보 10곳 · 반경 1km 에 모임 | 35.3 ms | 55.8 ms | 99.2 ms | 94,026 |
| 후보 10곳 · 서울 전역에 흩어짐 | 70.4 ms | 84.9 ms | 130.8 ms | 201,948 |
| 서울 전체 (멈추지 않음) | 74.0 ms | 86.7 ms | 129.8 ms | 213,579 |

후보를 다 확정하면 멈추는데, 확정한 노드는 전체 대비 모인 후보 44% · 흩어진 후보 95% 다. 멈추는 시점은 가장 먼 후보가 정한다 — 출발지가 서울 곳곳이면 후보가 모여 있어도 거기까지 가는 동안 도시 대부분을 훑는다.

## 3. CSR 대 객체 인접리스트

같은 그래프를 `List<List<Edge>>`(엣지마다 객체, 시간대 배열도 엣지마다)로 옮겨 같은 다익스트라·같은 힙으로 돌렸다. 서울 전체 탐색, 5판 번갈아 잰 판별 중앙값의 중앙값. 두 쪽의 거리 배열이 20개 출발지에서 모두 같음을 먼저 확인했다.

| | CSR (배열) | 객체 인접리스트 | 배 |
|---|---|---|---|
| 탐색 1회 (서울 전체) | 74.8 ms | 89.6 ms | 1.20× |
| 탐색에 쓰는 구조의 힙 | 9.5 MB | 28.2 MB | 3.0× |
| 엣지 하나당 | 16.3 B | 48.6 B | |

두 쪽 모두 탐색에 쓰는 것(이웃·가중치·시간대)만 센 값이다. 객체 쪽은 유리하게 만든 대조군이다 — 노드 번호가 0..N-1 int 이고, 엣지는 record, 리스트는 크기를 맞춰 잡았다. `Map<Long, List<Edge>>` 처럼 박싱된 키를 쓰면 이보다 커진다.

## 4. 행렬 API

방을 만들고 사람마다 출발지(서울 무작위 좌표)를, 후보는 한 동네(반경 1~3km)에 정한 뒤 `POST /rooms/{id}/matrix` 를 부른 응답시간. MockMvc 라 네트워크는 빠진다. 예열 3회 뒤 15회.

| 사람 × 후보 | 중앙값 | p95 | 서버 계산(elapsedMs 중앙값) | 확정 노드(합) |
|---|---|---|---|---|
| 2 × 5 | 95.4 ms | 140.5 ms | 90 ms | 201,171 |
| 5 × 10 | 253.5 ms | 279.5 ms | 247 ms | 664,600 |
| 10 × 20 | 374.8 ms | 415.6 ms | 367 ms | 1,024,247 |

다익스트라 횟수는 사람 수와 같고 후보 수와 무관하다(one-to-many).
