# 동시 요청 스윕 — 그래프를 어디에 두는가

`./gradlew sweepTest` 가 만든 결과(`server/build/reports/perf/concurrency.md`)를 옮겨 둔 것이다. 측정 코드는 `server/src/test/java/com/wherewego/routing/ConcurrencySweepTest.java`. 힙 512MB, 코어 16 개짜리 개발 머신에서 돌린 회차다 — 절대값(ms, req/s)은 서버에서 다시 재야 하고, 배수와 메모리 구성은 하드웨어가 바뀌어도 유지된다.

> 운영 서버(e2-small)에서 같은 측정을 돌린 결과는 [perf-server.md](perf-server.md). 메모리 구성과 힙 천장은 그대로였지만, **§3 의 작업공간 풀은 지연 득실이 반대로 나왔다** — 서버에서는 중앙값을 내주고 처리량을 산다.

- 측정 시각 2026-11-10T23:22:34
- JVM 25.0.4.1 · 최대 힙 512MB · 코어 16
- 시간대 19시 · 씨앗 42 · 후보 20곳(서울 전역) · 커넥션 풀 30 · 수준마다 요청 3×동시수

빌드 #22 · 노드 213,674 · 엣지 607,257

후보는 **서울 전역에 흩어뜨렸다**. 실제 방은 후보가 한 동네에 모이는 쪽이 많고 그러면 조기 종료가 더 먹어서 숫자가 좋아진다 — 여기서는 **불리한 쪽으로** 잡는다.

## 0. 메모리는 무엇으로 이루어지나

서울 전역 후보 20곳 탐색 1회의 모양: 확정 노드 **198,736** · 힙에 넣은 횟수 236,136 · 힙 최대 원소 8,628개.

| 항목 | 크기 | 동시 사용자에 비례하나 |
|---|---|---|
| JVM 베이스라인 (Spring · Hikari · JDBC) | 22 MB | 아니다 — 상수 |
| 공유 그래프 (CSR 배열, 불변) | **28.9 MB** | **아니다 — 상수** |
| `dist` `int[213,674]` | 0.82 MB | 그렇다 |
| `prevNode` `int[213,674]` | 0.82 MB | 그렇다 |
| `prevEdge` `int[213,674]` | 0.82 MB | 그렇다 |
| `wanted` `boolean[213,674]` | 0.20 MB | 그렇다 |
| `LongMinHeap` `long[16,384]` (최대 원소 8,628) | **0.13 MB** | 그렇다 |
| **탐색 1회 작업공간 합** | **2.77 MB** | **동시 탐색 수 × 이 값** |

그래프는 요청마다 복사되지 않는다. `GraphCache` 가 들고 있는 `volatile` 참조 하나를 모든 요청이 같이 읽는다(불변이라 잠금이 없다). **결과 캐시처럼 키가 늘면 커지는 구조가 아니다.**

그래서 `살아 있는 힙 = 베이스라인 + 그래프 + 동시 탐색 수 × 2.77 MB` 다. 앞의 두 항이 51 MB 를 먼저 먹으니 512MB 힙이면 산술적으로 **동시 탐색 166개**까지 들어간다.

**그런데 실제로는 그보다 훨씬 먼저 찬다.** §3 의 `요청마다 할당` 피크 힙이 산술 상한보다 훨씬 낮은 동시성에서 이미 힙 천장 근처에 붙는다. `살아 있는 양`과 `쓰는 양`이 다르기 때문이다 — 요청마다 2.77 MB 를 새로 잡고 버리므로 할당 속도가 초당 수백 MB 가 되고, G1 은 힙이 거의 찰 때까지 수거를 미룬다. 그래서 **한계를 정하는 것은 살아 있는 양이 아니라 할당 속도**이고, 아래에서 재는 `작업공간 풀` 이 바로 그 할당을 없애는 장치다.

### DB 간선 조회는 메모리를 아끼나

아니다. **탐색이 여전히 앱에서 돌기 때문에 작업공간은 똑같이 든다** — DB 로 옮긴 것은 이웃 정보뿐이다. 그 위에 질의마다 쓰레기가 더 생긴다. 같은 단위작업(노드 500개 확장)의 스레드 할당량을 재면:

확장 500회와 1,500회에서 각각 재서 **확장 횟수와 무관한 고정분**과 **확장 하나가 더 얹는 몫**을 갈라냈다.

세 번째 줄은 **쓰레기를 최소로 줄인 DB 방식**이다. 커넥션과 `PreparedStatement` 를 탐색 하나 동안 재사용하고, 결과를 리스트나 레코드로 옮기지 않고 `ResultSet` 에서 바로 완화하고, 파라미터 박싱도 없앴다 — `JdbcTemplate` 을 걷어낸 손수 JDBC 다.

| 방식 | 고정분 (작업공간) | 확장당 증가분 | 서울 전역 탐색 1회 총 할당 |
|---|---|---|---|
| 인메모리 CSR | 2.45 MB | 0 B | **2.5 MB** |
| DB 간선 조회 (`JdbcTemplate`) | 2.51 MB | 1535 B | 293 MB |
| DB 간선 조회 (쓰레기 최소화) | 2.45 MB | **773 B** | **149 MB** |

인메모리는 고정분이 거의 전부다 — 확장당 증가분이 0 B 로, 배열을 훑는 것 말고는 객체를 만들지 않는다.

객체를 안 만들면 어떻게 되나 — **확장당 1535 B 에서 773 B 로 2.0배 줄었다. 그런데 0 이 되지는 않는다.** 질의마다 드라이버가 `ResultSet` 과 와이어 프로토콜 버퍼를 만들어야 하고, 그건 애플리케이션 코드로 없앨 수 없다. 서울 전역 탐색 1회로 환산하면 인메모리 2.5 MB 대 **149 MB**, 여전히 약 61배다.

속도도 같이 좋아졌다. 구문을 재사용하니 파싱·플랜이 사라지고 풀에서 빌리는 비용도 없다 — 노드 500개 확장 1회가 182.8 ms → **172.4 ms**. 그래도 인메모리(0.3 ms)와는 자리가 다르다.

대가가 하나 생긴다. 커넥션을 탐색이 끝날 때까지 쥐고 있으므로 **동시 탐색 수가 커넥션 풀 크기(30)에 묶인다.** 질의마다 빌리고 돌려주면 그 제약은 없지만 그게 바로 줄이려던 비용이다 — 쓰레기와 동시성이 맞바꿔진다.

결론은 그대로다. 그래프를 DB 에 두면 **28.9 MB 를 아끼고**, 가장 알뜰하게 짜도 **탐색 1회에 149 MB 의 질의 쓰레기를 얻는다.** (이 측정의 DB 방식들도 노드 id ↔ 배열 첨자 변환 때문에 그래프를 들고 있다. 진짜로 29MB 를 아끼는 설계라면 그 변환을 따로 마련해야 한다.)

- 측정 JVM 최대 힙 **512 MB** · 코어 16

## 1. 먼저 — 두 방식이 같은 탐색을 하는가

출발지 3곳에서 노드 500 개를 확장한 뒤의 거리 배열이 인메모리와 DB 간선 조회에서 완전히 같다. 알고리즘·힙·확장 순서가 같고 **이웃을 어디서 읽는지만** 다르다.

확장당 비용은 동시 1 에서 0.4 ms, 동시 100 에서 3.9 ms 다. 아래 외삽은 **가장 한가한 쪽(0.4 ms)** 을 쓴다 — DB 에 유리한 값으로 잡는다.

**회차 간 차이.** 32 칸 중 가장 빠른 회차와 가장 느린 회차의 중앙값 차이가 1.5배를 넘은 칸은 **3 칸**이다. 가장 컸던 것은 `사전계산 조회` · 동시 4 의 **2.7배** — 그 칸은 세 회차 중 적어도 한 번은 간섭을 맞았고, 표에는 가장 빠른 회차가 들어갔다.

**작업공간 풀의 거래.** 동시 100 에서 `요청마다 할당` 대비 `작업공간 풀 16벌`: 피크 힙 503 MB → **155 MB**, GC 50 ms → **0 ms**. 중앙값 은 460.6 ms → 122.5 ms 로 **3.8배 좋아졌다**, p95 은 1277.7 ms → 1860.3 ms 로 **1.5배 나빠졌다**, 처리량은 178 → 143 req/s 로 **20% 줄었다**. 풀은 동시 탐색을 16 개로 묶어 나머지를 기다리게 하는 장치라, 메모리가 상수가 되는 대신 기다림이 응답시간 어디에 쌓이는지가 대가다.

## 4. 사전계산은 왜 못 쓰나 — 저장 비용

§3 에서 사전계산 조회가 가장 빨랐다. 답이 이미 표에 있으면 인덱스 조회 한 번이니 당연하다. 문제는 **그 표를 만들 수 있느냐**다. 출발지는 사용자가 찍는 임의 좌표라 스냅 대상 노드 전부가 출발지가 될 수 있다.

| 항목 | 값 |
|---|---|
| 스냅 대상 노드 (WALK 165,050 + STOP 11,446) | **176,496** |
| 전면 사전계산 행 수 (노드² × 24시간대) | **7.48e+11 행** |
| 행 48B 가정 시 용량 | **36 TB** |
| 역·정류장끼리만(STOP² × 24) | 3.14e+09 행 · 151 GB |
| 지금 그래프 전체 | 28.9 MB |

전면 사전계산은 TB 급이라 만들 수 없다. 역·정류장끼리만 미리 계산하는 쪽은 크기가 들어오지만, **출발지와 후보는 임의 좌표라 양쪽 끝의 보행 구간이 남는다** — 그 부분은 결국 탐색해야 하므로 인메모리 그래프가 그대로 필요하다. 사전계산은 인메모리를 **대체**하지 못하고 그 위에 얹는 캐시가 된다.

## 5. 그래서

- 인메모리로 **사는 것**은 SQL 실행 시간이 아니다. 탐색 1회가 노드 198,736 개를 확장하므로, 이웃을 DB 에서 읽으면 왕복이 그만큼 붙는다 — **질의 1번 대 198,736번**의 차이다. 이게 CRUD 와 경로탐색을 가르는 지점이다.
- 인메모리로 **내주는 것**은 인스턴스마다 붙는 29 MB, 콜드스타트, 그래프 교체 시점에 인스턴스끼리 다른 `build_id` 를 볼 수 있다는 점이다.
- 사용자가 늘 때 위험한 것은 그래프가 아니라 **탐색 작업공간**이다. 스레드별 재사용은 GC 만 없애고 상한은 그대로 둔다(스레드마다 한 벌). **작업공간 풀 16벌**이 그 비례를 상수로 바꾼다 — §3 의 피크 힙 열이 그 차이다.
- 풀의 대가(§3): 동시 100 에서 `요청마다 할당` 대비 `작업공간 풀 16벌`: 피크 힙 503 MB → **155 MB**, GC 50 ms → **0 ms**. 중앙값 은 460.6 ms → 122.5 ms 로 **3.8배 좋아졌다**, p95 은 1277.7 ms → 1860.3 ms 로 **1.5배 나빠졌다**, 처리량은 178 → 143 req/s 로 **20% 줄었다**. 풀은 동시 탐색을 16 개로 묶어 나머지를 기다리게 하는 장치라, 메모리가 상수가 되는 대신 기다림이 응답시간 어디에 쌓이는지가 대가다.
- 사전계산 + SQL 조회가 가장 빠르지만 전면 적용은 저장 비용이 막는다. **트래픽이 더 늘면 인메모리를 버리는 게 아니라 그 위에 인기 OD 캐시를 얹는다.**
