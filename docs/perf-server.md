# 운영 서버 성능 측정 — GCP e2-small

개발 머신(16 코어)에서 잰 [동시 요청 스윕](perf-concurrency.md)·[알고리즘 대조](perf-algorithms.md)를 **운영
서버에서 그대로** 다시 돌렸다. 배수와 메모리 구성은 하드웨어가 바뀌어도 같은지, 절대값(ms, req/s)과 포화
지점은 이 서버에서 얼마인지를 보려는 측정이다. 원자료는 [perf-server/](perf-server/) 에 있다.

> **한 줄 결론** — 운영 서버에서도 그래프를 메모리에 두는 게 맞다는 결론은 그대로였다. 다만 서버는 동시 요청
> 2개에서 초당 8건으로 포화했고, 후보가 서울 전역에 흩어지면 행렬 한 줄이 20ms 가 아니라 235ms 로 꺾였다.

| | |
|---|---|
| 서버 | GCP **e2-small** · vCPU 2 (AMD EPYC 7B12, 공유 코어) · 메모리 1,959MB + 스왑 2GB |
| 비교 대상 | 개발 머신 · Intel i7-1260P (16 스레드) |
| 측정 | 2026-11-11 · 커밋 `a0349e8` · 그래프 빌드 #22 · JDK 25.0.5 |
| 힙 | 스윕 512MB (운영 서버가 `-Xmx` 없이 뜰 때 JVM 이 잡는 값과 같다) · 알고리즘 768MB |
| 방법 | [`deploy/perf/run-on-server.sh --twice`](../deploy/perf/run-on-server.sh). 측정하는 동안 서버 컨테이너를 내려서, 측정 JVM 이 앱 자리에 서는 "VM 하나에 앱 하나 + DB" 구조로 쟀다. 링크를 돌리기 전이라 사용자는 없었다 |
| 빠진 것 | pgRouting 대조 — 동시 16 에서 DB 안에 간선 60만 개짜리 그래프를 16벌 지으면 2GB 를 넘을 수 있어 뺐다 |

동시 요청 스윕은 세 번 돌았다. 1회차는 두 번째 스윕 도중 끊겼고, 끝난 스윕까지는 저장돼 있다.

| | 언제 | 서버 상태 |
|---|---|---|
| **A** | 00:16 ~ 00:42 | 다운로드·알고리즘 측정 뒤 — 셋 중 가장 쉬던 상태 |
| **B** | 01:00 ~ 01:25 | 그 뒤 35분 넘게 달린 다음 |
| **C** | 01:25 ~ 01:50 | B 바로 뒤 |

## 1. 버스트 제한은 없었다

e2-small 은 공유 코어라, 부하가 오래가면 VM 이 CPU 를 덜 줄 수 있다. 그래서 같은 스윕을 쉬던 상태부터 지친
상태까지 세 번 놓고 비교했다.

| | A | B | C |
|---|---|---|---|
| 행렬 한 줄 (동시 1, 후보 서울 전역) | 237.3 ms | 236.1 ms | 234.5 ms |
| 처리량 상한 (`요청마다 할당`) | 7 req/s | 8 req/s | 8 req/s |
| steal (하이퍼바이저가 CPU 를 안 준 비율) | **0% (최대 0%)** | **0% (최대 0%)** | **0% (최대 0%)** |

두 회차의 `vmstat` 표본 1,121개(5초 간격) 중 steal 이 0 을 넘은 것은 하나도 없고, 1시간 반 동안 CPU 를 꽉
써도 숫자가 그대로였다. **이 부하에서 e2-small 은
vCPU 2 개를 다 준다.** 처리량 상한 8 req/s 가 `vCPU 2 개 ÷ 탐색 0.235초 = 8.5` 와 맞는다는 것도 같은 얘기다.

## 2. 용량 — 후보가 어디 있느냐에 따라 10배 갈린다

| 행렬 한 줄 (동시 1) | 개발 머신 | **운영 서버** |
|---|---|---|
| 후보가 한 동네 (반경 1km — 실제 방의 모양) | 16.4 ms | **19.6 ms** |
| 후보가 서울 전역 (최악) | 27.9 ms | **236.9 ms** |

동시 요청을 올리면 (B, 후보 서울 전역, `요청마다 할당`):

| 동시 요청 | 1 | 2 | 4 | 8 | 16 | 32 | 64 | 100 |
|---|---|---|---|---|---|---|---|---|
| 처리량 (req/s) | 5 | **8** | 8 | 7 | 7 | 7 | 7 | 7 |
| 응답시간 중앙값 | 236 ms | 246 ms | 456 ms | 786 ms | 1.8 s | 3.9 s | 3.5 s | 5.2 s |

**동시 2 (= vCPU 수) 에서 포화한다.** 개발 머신은 16 에서 포화했다. 그 뒤로는 처리량이 그대로고 응답시간만
늘어난다 — 탐색이 CPU 바운드라는 것이 서버에서도 확인된다.

사용자가 겪을 숫자로 바꾸면(산술 — 행렬은 사람 수만큼 탐색을 순서대로 돈다):

| 10명짜리 행렬 하나 | |
|---|---|
| 후보가 한 동네 | 약 **0.2초** |
| 후보가 서울 전역 | 약 **2.4초** |

## 3. 탐색 비용이 어느 지점에서 꺾인다 — 원인은 아직 모른다

서버가 일정하게 느린 게 아니다. 노드 하나를 확정하는 데 드는 시간으로 보면:

| 확정 노드 | 개발 머신 | 운영 서버 | 서버 / 개발 |
|---|---|---|---|
| 83,388 (목적지 1곳, 한 동네) | 0.18 µs | 0.22 µs | 1.2× |
| 91,260 (후보 20곳, 한 동네) | 0.18 µs | 0.21 µs | 1.2× |
| 124,268 (목적지 1곳, 서울 전역) | 0.20 µs | 0.24 µs | 1.2× |
| **192,697** (후보 20곳, 서울 전역) | 0.14 µs | **1.23 µs** | **8.5×** |

개발 머신은 탐색이 커져도 노드당 비용이 그대로인데, 운영 서버는 **그래프(노드 213,674)를 거의 다 훑는 순간
5배로 뛴다.** 두 회차 모두 같았다.

- **스왑 때문은 아닌 것 같다.** 스왑이 심하던 1회차 알고리즘 측정(233.2 ms)과 스왑이 거의 없던 2회차 스윕
  구간(236.1 ms)이 같은 값이었다.
- **가장 유력한 가설은 공유 호스트의 메모리 계층이다.** 그래프 전체(배열 약 22MB)를 훑으면 이 VM 이 실제로 쓸
  수 있는 CPU 캐시를 넘어서 메모리까지 가는데, 그 메모리를 다른 VM 과 나눠 쓴다. 확인하지 않은 가설이다.
- **가르는 방법:** 같은 측정을 전용 코어 인스턴스(e2-standard-2)에서 돌린다. 거기서 꺾임이 사라지면 공유
  호스트 탓이다.

## 4. 작업공간 풀 — 지연 득실이 개발 머신과 반대로 나왔다

풀은 동시 탐색을 코어 수만큼(개발 머신 16벌, 서버 2벌)으로 묶고 작업공간을 돌려쓴다. 동시 100 에서
`요청마다 할당` 대비:

| | 개발 머신 | 서버 A | 서버 B | 서버 C |
|---|---|---|---|---|
| 피크 힙 | 503 → **155 MB** | 507 → **109 MB** | 406 → **109 MB** | 508 → **112 MB** |
| GC | 50 → **0 ms** | 38 → **0 ms** | 50 → **0 ms** | 283 → **0 ms** |
| 중앙값 | **3.8배 좋아짐** | **2.9배 나빠짐** | **2.3배 나빠짐** | **2.6배 나빠짐** |
| 처리량 | 20% 줄어듦 | **33% 늘어남** | **14% 늘어남** | **14% 늘어남** |
| p95 | 1.5배 나빠짐 | 1.3배 나빠짐 | 1.5배 좋아짐 | 1.7배 나빠짐 |

- **메모리 이득은 어디서나 같다** — 피크 힙이 동시 요청과 무관한 상수가 되고 GC 가 0 이 된다
- **중앙값과 처리량은 정반대로 나왔다.** 개발 머신에서는 중앙값을 사고 처리량을 내줬는데, 서버에서는 처리량을
  사고 중앙값을 내준다. 세 회차 모두 같은 방향이다
- **p95 는 결론을 낼 수 없다.** 세 회차 중 둘은 나빠지고 하나는 좋아졌다

개발 머신에서 내린 "풀은 꼬리지연을 내주고 중앙값을 산다"는 그 머신에서만 맞는 말이었다. **직접 재보지 않은
하드웨어에 대한 결론은 믿을 수 없다** — 이번 측정에서 얻은 가장 값진 교훈이다.

## 5. 하드웨어가 바뀌어도 그대로인 것

개발 머신에서 "하드웨어와 무관하다"고 예상한 것들이 서버에서도 그대로 나왔다.

| | 개발 머신 | 운영 서버 |
|---|---|---|
| 탐색 1회 작업공간 | 2.77 MB | 2.77 MB |
| 공유 그래프 | 29.0 MB | 29.0 MB |
| DB 간선 조회의 질의 쓰레기 (탐색 1회, 손수 JDBC) | 149 MB · 확장당 773 B | 149 MB · 확장당 773 B |
| `요청마다 할당` 이 힙 천장(512MB)에 닿는 동시 요청 | 64 | 64 |
| A* 휴리스틱이 실제 소요시간을 설명하는 몫 | 12.2% | 12.2% |
| A* 가 목적지 1곳에서 다익스트라보다 빠른 배수 | 1.07~1.24× | 1.13~1.23× |

## 6. DB 간선 조회 — 서버에서는 더 나쁘다

| | 개발 머신 | 운영 서버 |
|---|---|---|
| 확장당 비용 (동시 1) | 0.37 ms | **1.0 ms** |
| 확장당 비용 (동시 100) | 3.9 ms | **50.6 ms** |
| 인메모리 대비 (노드 500개 확장, 동시 1) | 약 460배 | 약 1,200배 |
| 행렬 한 줄 외삽 (확장 198,736회 × 동시 1 의 확장당 비용) | 약 73초 | **약 191초** |

서버에서는 측정 JVM 과 Postgres 가 vCPU 2 개를 나눠 쓰고, 남은 메모리가 적어 Postgres 의 페이지 캐시도
작다. 질의 하나하나가 느려지고 그게 확장 횟수만큼 곱해진다.

## 7. 메모리와 스왑

| | |
|---|---|
| 측정 중 남은 메모리 | 대부분 **70~100 MB** |
| 스왑에 들어가 있던 양 | 350~590 MB |
| DB 컨테이너 메모리 | 111 ~ 289 MB |

큰 스왑은 **단계가 바뀌는 순간**(측정 JVM 이 내려가고 새로 뜰 때)에 몰려 있었다. CPU 가 꽉 찬 측정
한가운데서 들어온 스왑은 분당 수 KB 였다. 그래서 측정이 오염된 정도는 작다고 본다. 다만 2GB 서버에서 측정
JVM, Gradle, DB 가 같이 돌면 빠듯하다. 운영 중에는 Gradle 이 없으니 그보다 여유가 있다.

## 8. 이 측정이 보지 못하는 것

- **하네스는 탐색 함수만 잰다.** 실제 요청은 Caddy → Tomcat → 세션 → JSON → 방·후보 조회 → 스냅 → 탐색 →
  JSON 이다. vCPU 2 개에서는 나머지 몫도 작지 않을 수 있다. 다른 머신에서 HTTP 로 부하를 거는 측정이 다음
  단계다 — 그 자리에서 "경로탐색이 로그인을 느리게 하나"도 같이 잴 수 있다
- **pgRouting 과 DB 쪽 메모리** — 동시 수준을 코어 수로 묶으면 서버에서도 안전하게 잴 수 있다
- **§3 의 꺾임의 원인**
- 서버 쪽 지연 칸은 개발 머신보다 흔들린다 — B 는 32칸 중 8칸이 회차 간 1.5배 넘게 차이 났다(가장 컸던 칸은
  사전계산 조회 · 동시 64 의 13.5배, 1ms 아래 값이라 결론에는 영향이 없다). 그래서 이 문서는 **세 회차가
  같은 방향인 것만** 결론으로 썼다
